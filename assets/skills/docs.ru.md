# Навык: документация

Цель — текст, по которому человек **сможет повторить действие**, а не перечень
очевидностей. Документация пишется для конкретного читателя и версии продукта.

## 1. Перед написанием
1. Определи читателя: новичок, опытный пользователь, разработчик.
2. Определи цель: установить, настроить, интегрировать, починить.
3. Собери факты из существующих файлов, кода и конфигурации. Не выдумывай
   команды, пути, флаги, версии, ограничения и поведение.
4. Если чего-то не знаешь — проверь или честно пометь «не проверено».

## 2. Структура
1. Что это и зачем (2–4 предложения).
2. Требования: ОС, версии, права доступа.
3. Установка или подключение — пошагово.
4. Быстрый старт: минимальный рабочий пример.
5. Основные сценарии использования.
6. Справочник: параметры, команды, поля, форматы.
7. Ограничения и безопасность.
8. Проблемы и их решение.
9. Changelog или «что дальше».

Каждый шаг начинай с глагола: «Нажми», «Вставь», «Запусти».
Один шаг = одно действие. Не смешивай проверку и настройку в одном пункте.

## 3. Формат
- Markdown: `.md` через `write`; DOCX/PDF — через `doc`.
- Заголовки `#`/`##`/`###`, без пропуска уровней.
- Код — в ``` с языком: ```bash, ```json, ```http.
- Пути и имена — моноширинные: `/sdcard/Download/FunaFiles`.
- Предупреждения — отдельным блоком **Внимание:** или **Безопасность:**,
  а не в конце абзаца.
- Таблицы в Markdown допустимы; в DOCX/PDF — нет (см. навыки docx/pdf).
- Ссылки — на реальные файлы и разделы, не на выдуманные URL.
- Один язык на весь документ; термины одинаковые.

## 4. Пример README
```markdown
# Название

Одно предложение: что делает продукт.

## Требования
- Android 8.0+
- 50 МБ свободного места

## Быстрый старт
1. Установи APK.
2. Открой приложение и войди.
3. Отправь первое сообщение.

## Настройка
- **Адрес** — по умолчанию `http://127.0.0.1:8787`.
- **Ключ** — выдаётся в Настройках.

## Проблемы
### Сервер не отвечает
Проверь, что приложение открыто и порт свободен.
```

## 5. Точность
- Команды копируются как есть: без «примерно» и лишних пробелов.
- Если показан вывод — пометь, что это пример, и не выдумывай полный лог.
- Секреты (токены, пароли, ключи) — только как `fk-…`, `sk-…`, без реальных
  значений.
- Числа и лимиты берутся из кода или конфигурации, а не из памяти.
- Версии — из `build.sh`/manifest, не из догадок.

## 6. Проверка перед выдачей
- Пройди документ глазами новичка: хватит ли шагов, чтобы дойти до результата?
- Каждая команда указывает, где её выполнять (телефон, терминал, ПК).
- Каждая ссылка ведёт на существующий файл или раздел.
- Нет противоречий между разделами.
- Нет выдуманных функций «на будущее» без пометки «план».

## 7. Чек-лист
- [ ] Есть цель, читатель и требования.
- [ ] Есть минимальный рабочий пример.
- [ ] Шаги последовательны, с глаголами в начале.
- [ ] Команды, пути и лимиты соответствуют реальному продукту.
- [ ] Нет секретов и выдуманных источников.
- [ ] Есть раздел проблем и следующих шагов.
